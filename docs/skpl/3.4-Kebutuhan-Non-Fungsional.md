# 3.4 Kebutuhan Non-Fungsional

**Dokumen:** SKPL — Sistem Informasi Yayasan Karinakas (SIKAS)
**Bagian:** Bab III Kebutuhan Rinci · Subbab 3.4
**Berkas induk:** [SKPL.md](../../SKPL.md) · **Berkas terkait:** [3.2 Kebutuhan Fungsional](3.2-Kebutuhan-Fungsional.md) · [3.3 Diagram Use Case](3.3-Diagram-Use-Case.md)

---

Subbab ini menguraikan kebutuhan non-fungsional SIKAS. Setiap kebutuhan dinyatakan dalam bentuk yang **terukur** sehingga dapat diverifikasi pada tahap pengujian. Nilai acuan ditetapkan dengan mempertimbangkan skala operasional lembaga sosial sebagaimana asumsi A-06 pada Subbab 2.5.

---

## 3.4.1 Performance

| | | |
|---|---|---|
| **ID Requirement** | : | NFR 3.4.1.1 |
| **Deskripsi** | : | Sekurang-kurangnya 95% permintaan pembacaan data non-media harus ditanggapi layanan dalam waktu maksimal **1 detik**, diukur pada peladen dengan volume data sampai 1.000 baris per tabel dan koneksi jaringan minimal 5 Mbps. |
| **Rasional** | : | Pengelola melakukan penelusuran dan penyaringan data secara berulang saat memverifikasi donasi dan relawan. Tanggapan yang lambat membuat proses verifikasi harian terasa berat dan mendorong pengelola kembali mencatat secara manual. |

| | | |
|---|---|---|
| **ID Requirement** | : | NFR 3.4.1.2 |
| **Deskripsi** | : | Halaman publik harus menampilkan konten pertama (*First Contentful Paint*) dalam waktu maksimal **3 detik** pada koneksi seluler 4G. Ukuran berkas aplikasi hasil pembangunan tidak boleh melebihi **250 kB** dalam keadaan terkompresi *gzip*. |
| **Rasional** | : | Sebagian besar pengunjung mengakses melalui telepon pintar dengan kualitas jaringan yang beragam. Halaman yang lambat menyebabkan calon donatur dan relawan meninggalkan situs sebelum informasi tersaji, sehingga sasaran peningkatan partisipasi tidak tercapai. |

| | | |
|---|---|---|
| **ID Requirement** | : | NFR 3.4.1.3 |
| **Deskripsi** | : | Seluruh daftar data pada panel pengelolaan harus menerapkan penomoran halaman dengan maksimal **100 baris per permintaan**, sehingga waktu muat tidak bertambah sebanding dengan pertumbuhan jumlah data. |
| **Rasional** | : | Jumlah donasi, relawan, dan foto dokumentasi bertambah terus sepanjang operasional lembaga. Tanpa pembatasan per halaman, halaman pengelolaan akan makin lambat dari waktu ke waktu meskipun tidak ada perubahan program. |

| | | |
|---|---|---|
| **ID Requirement** | : | NFR 3.4.1.4 |
| **Deskripsi** | : | Pengunggahan massal **100 foto** berukuran maksimal 5 MB harus selesai dalam waktu maksimal **5 menit** pada kecepatan unggah minimal 5 Mbps, dengan pengiriman dipecah maksimal 20 berkas per permintaan. |
| **Rasional** | : | Satu kegiatan dapat menghasilkan ratusan foto dokumentasi. Batas waktu ini memastikan dokumentasi dapat dipublikasikan pada hari yang sama tanpa menyita seluruh waktu kerja pengelola. |

| | | |
|---|---|---|
| **ID Requirement** | : | NFR 3.4.1.5 |
| **Deskripsi** | : | Pembentukan berkas rekapitulasi berisi sampai **1.000 baris** harus selesai dalam waktu maksimal **5 detik** terhitung sejak tombol ekspor ditekan hingga berkas terunduh. |
| **Rasional** | : | Rekapitulasi disusun saat menjelang tenggat pelaporan lembaga. Proses yang lama membuat pengelola ragu memakai fitur ini dan kembali menyalin data secara manual. |

## 3.4.2 Reliability

| | | |
|---|---|---|
| **ID Requirement** | : | NFR 3.4.2.1 |
| **Deskripsi** | : | Sistem harus tersedia sekurang-kurangnya **99% per bulan**, atau setara dengan ketidaktersediaan maksimal **8 jam per bulan** di luar pemeliharaan terjadwal yang diumumkan sebelumnya. |
| **Rasional** | : | Donasi dan pendaftaran relawan dapat diajukan kapan saja, termasuk di luar jam kerja lembaga. Ketidaktersediaan sistem berarti hilangnya kesempatan partisipasi yang tidak dapat dipulihkan. |

| | | |
|---|---|---|
| **ID Requirement** | : | NFR 3.4.2.2 |
| **Deskripsi** | : | Kegagalan pengiriman notifikasi surel **tidak boleh** membatalkan perubahan status yang telah tersimpan. Toleransi kegagalan adalah **0 transaksi** verifikasi yang batal akibat gangguan layanan surel. |
| **Rasional** | : | Pengiriman surel bergantung pada layanan pihak ketiga di luar kendali lembaga (kebergantungan D-02). Bila kegagalan surel ikut membatalkan verifikasi, data pendaftaran menjadi tidak konsisten dan pengelola harus mengulang pekerjaan. |

| | | |
|---|---|---|
| **ID Requirement** | : | NFR 3.4.2.3 |
| **Deskripsi** | : | Setiap kegagalan permintaan data harus disampaikan sebagai pesan berbahasa Indonesia yang dapat dipahami pengguna awam. Tidak boleh terdapat halaman kosong tanpa keterangan maupun pesan kesalahan mentah dari kerangka kerja (**0 kejadian**). |
| **Rasional** | : | Pengguna lembaga tidak memiliki latar belakang teknis. Pesan kesalahan mentah menimbulkan kesan sistem rusak dan mendorong pengguna berhenti memakainya, padahal gangguannya bersifat sementara. |

| | | |
|---|---|---|
| **ID Requirement** | : | NFR 3.4.2.4 |
| **Deskripsi** | : | Pengunggahan massal yang gagal sebagian tidak boleh membatalkan berkas yang telah tersimpan. Sistem harus melaporkan jumlah berkas berhasil dan gagal secara terpisah dengan ketepatan **100%**. |
| **Rasional** | : | Pengiriman dipecah menjadi beberapa permintaan, sehingga satu kegagalan jaringan di tengah proses berpotensi membatalkan puluhan foto yang sudah tersimpan bila tidak ditangani. |

| | | |
|---|---|---|
| **ID Requirement** | : | NFR 3.4.2.5 |
| **Deskripsi** | : | Pencadangan basis data beserta folder penyimpanan berkas harus dilakukan sekurang-kurangnya **satu kali per minggu**, sehingga kehilangan data maksimal (*Recovery Point Objective*) tidak melebihi **7 hari**. |
| **Rasional** | : | Bukti pembayaran donasi dan dokumentasi kegiatan merupakan arsip pertanggungjawaban lembaga yang tidak dapat dibuat ulang apabila hilang. |

| **ID Requirement** | : | NFR 3.4.3.1 |

| **Rasional** | : | Lembaga tidak memiliki staf teknologi informasi. Ketergantungan pada pengembang membuat sistem tidak dapat dioperasikan secara berkelanjutan setelah masa penelitian berakhir. |

| | | |
|---|---|---|
| **ID Requirement** | : | NFR 3.4.3.4 |

| **Rasional** | : | Diperlukan ukuran kebergunaan yang baku dan dapat dibandingkan sebagai bukti keberhasilan penerapan pendekatan *Human-Centered Design*, bukan sekadar penilaian subjektif. |

| | | |
|---|---|---|

| **Rasional** | : | Penghapusan bersifat permanen dan menyangkut data pihak lain seperti donasi dan pendaftaran relawan. Konfirmasi mencegah kehilangan data akibat kekeliruan operasional pengelola. |

| | | |

| **Rasional** | : | Tingkat literasi digital pengguna beragam. Istilah teknis berbahasa asing menghambat pemahaman dan menurunkan kepercayaan calon donatur terhadap proses yang sedang dijalaninya. |

## 3.4.4 Security

| | | |
|---|---|---|
| **ID Requirement** | : | NFR 3.4.4.1 |
| **Deskripsi** | : | Kata sandi harus terdiri atas sekurang-kurangnya **8 karakter** pada **seluruh** jalur penetapan kata sandi, yaitu pendaftaran akun, penggantian kata sandi, penyetelan ulang oleh super admin, dan pemulihan kata sandi. |
| **Rasional** | : | Akun pengguna menaungi data pribadi dan riwayat donasi. Ketentuan panjang minimum yang berbeda antarjalur membuka celah karena penyerang cukup memilih jalur dengan ketentuan paling longgar. |

| | | |
|---|---|---|
| **ID Requirement** | : | NFR 3.4.4.2 |
| **Deskripsi** | : | Kata sandi harus disimpan dalam bentuk teracak satu arah (*hash*) menggunakan algoritma bcrypt dan **tidak pernah** dikembalikan pada tanggapan layanan mana pun (**0 kejadian**). |
| **Rasional** | : | Apabila basis data bocor, kata sandi yang tersimpan sebagai teks biasa memungkinkan penyerang mengakses akun pengguna pada layanan lain karena kebiasaan memakai kata sandi yang sama. |

| | | |
|---|---|---|
| **ID Requirement** | : | NFR 3.4.4.3 |
| **Deskripsi** | : | Seluruh titik akhir layanan pengelolaan harus menolak permintaan bertoken bukan pengelola dengan tanggapan `403`, dan permintaan tanpa token dengan tanggapan `401`. Tingkat pemenuhan wajib **100%** dari titik akhir yang diuji. |
| **Rasional** | : | Pembatasan yang hanya diterapkan pada antarmuka dapat ditembus dengan memanggil layanan secara langsung, sebagaimana dikekang pada K-15 Subbab 2.4. |

| | | |
|---|---|---|
| **ID Requirement** | : | NFR 3.4.4.4 |
| **Deskripsi** | : | Data nominal donasi beserta detail pembayarannya (biaya, kode transaksi, rekening pengirim, dan berkas bukti) **tidak boleh muncul** pada tanggapan layanan bagi pengguna berperan admin, baik pada daftar donasi, hasil pencarian, maupun statistik dasbor (**0 kebocoran**). |
| **Rasional** | : | Kerahasiaan data keuangan merupakan pembeda kewenangan utama antara Admin dan Super Admin. Penyembunyian pada tampilan saja tidak cukup karena data tetap dapat dibaca melalui alat pengembang peramban. |

| | | |
|---|---|---|
| **ID Requirement** | : | NFR 3.4.4.5 |
| **Deskripsi** | : | Percobaan masuk ke sistem harus dibatasi maksimal **5 kali per menit** untuk setiap alamat IP, demikian pula permintaan pendaftaran akun dan permintaan tautan pemulihan kata sandi. Permintaan berikutnya ditolak dengan tanggapan `429` sampai jeda waktu terlampaui. Pembatasan harus memakai jatah yang **terpisah untuk tiap kelompok rute**, sehingga pemakaian wajar pada satu kelompok — misalnya memuat ulang halaman penyetelan ulang kata sandi — tidak ikut memblokir kelompok lain. |
| **Rasional** | : | Tanpa pembatasan laju, kata sandi dapat ditebak secara otomatis dalam jumlah tak terbatas. Akun super admin merupakan sasaran paling bernilai karena memiliki akses ke seluruh data keuangan dan data pribadi. |

| | | |
|---|---|---|
| **ID Requirement** | : | NFR 3.4.4.6 |
| **Deskripsi** | : | Pada lingkungan produksi, sistem wajib dijalankan melalui **HTTPS**, dengan daftar asal permintaan (*CORS*) dibatasi hanya pada ranah lembaga, dan mode awakutu (`APP_DEBUG`) dalam keadaan nonaktif. |
| **Rasional** | : | Token akses dikirim pada setiap permintaan sehingga dapat disadap bila jalur tidak terenkripsi. Mode awakutu yang aktif menampilkan jejak galat berisi struktur basis data dan konfigurasi peladen kepada publik. |

| | | |
|---|---|---|
| **ID Requirement** | : | NFR 3.4.4.7 |
| **Deskripsi** | : | Berkas unggahan hanya boleh diterima dalam bentuk berkas gambar dengan ukuran maksimal **4 MB** untuk bukti pembayaran dan **5 MB** untuk foto dokumentasi. Berkas disimpan menggunakan nama yang dibangkitkan sistem, bukan nama asli dari pengguna. |
| **Rasional** | : | Pembatasan jenis berkas mencegah pengunggahan berkas yang dapat dieksekusi peladen. Penggantian nama berkas mencegah penimpaan berkas lain dan menutup penyingkapan informasi dari nama berkas asli. |

| | | |
|---|---|---|
| **ID Requirement** | : | NFR 3.4.4.8 |
| **Deskripsi** | : | Seluruh tindakan pengelola yang mengubah data harus tercatat pada jejak audit dengan kelengkapan **100%**, memuat pelaku, jenis tindakan, objek, dan waktu kejadian. |
| **Rasional** | : | Beberapa pengelola menggunakan sistem secara bersamaan. Tanpa jejak audit, perubahan status donasi tidak dapat dipertanggungjawabkan apabila di kemudian hari terjadi perselisihan. |

## Catatan penyusunan

**Angka acuan tidak dikarang.** Nilai yang dapat diperiksa dari kode dikutip apa adanya, yaitu ukuran berkas hasil pembangunan, batas ukuran unggahan, pemecahan 20 berkas per permintaan, dan ukuran huruf dasar. Nilai yang bersifat target kinerja dan kebergunaan **wajib dibuktikan melalui pengujian**, dan pada tabel status ditandai sebagai "Diuji" agar tidak diklaim terpenuhi tanpa bukti.

**Dua kebutuhan keamanan semula tidak terpenuhi dan kini sudah diperbaiki.** NFR 3.4.4.1 muncul karena pendaftaran akun sempat menerima kata sandi 6 karakter sementara penggantian kata sandi menuntut 8 karakter, sedangkan NFR 3.4.4.5 muncul karena belum ada pembatasan laju pada rute mana pun. Keduanya ditemukan melalui pemeriksaan kode saat penyusunan dokumen ini, lalu diperbaiki dan diuji: panjang minimum kini seragam 8 karakter di seluruh jalur, dan percobaan masuk keenam dalam satu menit dibalas `429`. Urutan temuan-perbaikan-verifikasi tersebut dapat dijadikan bahan pembahasan pada bab hasil.

**Skor SUS pada NFR 3.4.3.4** dicantumkan karena penelitian ini menggunakan pendekatan *Human-Centered Design*, sehingga diperlukan ukuran kebergunaan yang baku dan dapat dibandingkan. Batas 68 merupakan nilai rata-rata yang lazim dipakai sebagai ambang keberterimaan.
