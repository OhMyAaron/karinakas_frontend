# 3.2 Kebutuhan Fungsional

**Dokumen:** SKPL — Sistem Informasi Yayasan Karinakas (SIKAS)
**Bagian:** Bab III Kebutuhan Rinci · Subbab 3.2
**Berkas induk:** [SKPL.md](../../SKPL.md) · **Berkas terkait:** [3.1 Kebutuhan Antarmuka Eksternal](3.1-Kebutuhan-Antarmuka-Eksternal.md) · [3.3 Diagram Use Case](3.3-Diagram-Use-Case.md)

---

Subbab ini menguraikan kebutuhan fungsional rinci Sistem Informasi Yayasan Karinakas (SIKAS). Setiap kebutuhan diberi nomor identitas dengan pola `FR SIKAS <nomor>` dan merupakan penjabaran dari fungsi produk yang telah diuraikan pada Subbab 2.2.

Penomoran dikelompokkan per ratusan: **100** publikasi informasi, **200** pengelolaan akun, **300** partisipasi masyarakat, **400** pengelolaan konten, **500** verifikasi dan pengawasan, **600** pelaporan.

---

## B. Kelompok Pengelolaan Akun Pengguna — penjabaran F-05 sampai F-07

### 3.2.12 Mencatat Registrasi Akun Pengguna
| | | |
|---|---|---|
| **ID Requirement** | : | FR SIKAS 201 |
| **Deskripsi** | : | Fungsi ini harus memampukan calon pengguna membuat akun melalui dua tahap. Tahap pertama menghimpun nama lengkap, surel, nama pengguna, dan kata sandi beserta konfirmasinya. Tahap kedua menghimpun data pribadi berupa jenis kelamin, tanggal lahir, nomor telepon, alamat, kota, dan asal paroki. Pengguna dapat kembali ke tahap pertama tanpa kehilangan data yang telah diisi. |

### 3.2.13 Memvalidasi Keunikan Identitas Akun
| | | |
|---|---|---|
| **ID Requirement** | : | FR SIKAS 202 |
| **Deskripsi** | : | Fungsi ini harus memeriksa bahwa surel dan nama pengguna yang didaftarkan belum digunakan akun lain, serta memastikan konfirmasi kata sandi sesuai dengan kata sandi yang dimasukkan. Apabila pemeriksaan gagal, sistem harus menolak pendaftaran dan menampilkan pesan kesalahan yang menjelaskan penyebabnya. |

### 3.2.14 Melakukan Autentikasi Pengguna
| | | |
|---|---|---|
| **ID Requirement** | : | FR SIKAS 203 |
| **Deskripsi** | : | Fungsi ini harus memampukan pengguna masuk ke sistem menggunakan surel maupun nama pengguna beserta kata sandi. Apabila kredensial sesuai, sistem menerbitkan token akses dan menyimpannya pada peramban pengguna. Apabila tidak sesuai, sistem menolak masuk dan menampilkan pesan kesalahan tanpa menyebutkan bagian kredensial mana yang keliru. |

### 3.2.15 Memulihkan Sesi Pengguna
| | | |
|---|---|---|
| **ID Requirement** | : | FR SIKAS 204 |
| **Deskripsi** | : | Fungsi ini harus memulihkan sesi pengguna secara otomatis ketika halaman dimuat ulang, dengan memvalidasi token yang tersimpan pada peramban terhadap layanan peladen, sehingga pengguna tidak perlu masuk kembali. |

### 3.2.16 Membatasi Akses Halaman Terproteksi
| | | |
|---|---|---|
| **ID Requirement** | : | FR SIKAS 205 |
| **Deskripsi** | : | Fungsi ini harus mengalihkan pengguna yang belum masuk ke halaman autentikasi ketika mengakses halaman yang menuntut sesi aktif, yaitu pengajuan donasi, pendaftaran relawan, dan profil. Setelah berhasil masuk, pengguna harus diarahkan kembali ke halaman tujuan semula, bukan ke halaman beranda. |

### 3.2.17 Membatasi Akses Panel Pengelolaan
| | | |
|---|---|---|
| **ID Requirement** | : | FR SIKAS 206 |
| **Deskripsi** | : | Fungsi ini harus menolak akses ke panel pengelolaan bagi pengguna yang tidak berperan sebagai admin maupun super admin, baik ketika halaman diakses melalui tautan maupun melalui pengetikan alamat secara langsung. Penolakan juga harus diberlakukan pada sisi layanan atas setiap permintaan data pengelolaan. |

### 3.2.18 Mengakhiri Sesi Pengguna
| | | |
|---|---|---|
| **ID Requirement** | : | FR SIKAS 207 |
| **Deskripsi** | : | Fungsi ini harus mengakhiri sesi pengguna, mencabut token akses pada sisi peladen, serta menghapus token yang tersimpan pada peramban sehingga halaman terproteksi tidak dapat diakses kembali. |

### 3.2.19 Memutakhirkan Data Profil Pengguna
| | | |
|---|---|---|
| **ID Requirement** | : | FR SIKAS 208 |
| **Deskripsi** | : | Fungsi ini harus memampukan pengguna memperbarui data pribadinya, meliputi nama lengkap, nomor telepon, alamat, kota, asal paroki, dan keterangan diri. Perubahan disimpan pada basis data dan langsung digunakan sebagai data acuan pada formulir pendaftaran relawan. |

### 3.2.20 Mengganti Kata Sandi
| | | |
|---|---|---|
| **ID Requirement** | : | FR SIKAS 209 |
| **Deskripsi** | : | Fungsi ini harus memampukan pengguna mengganti kata sandi dengan memasukkan kata sandi lama, kata sandi baru, dan konfirmasinya. Sistem menolak penggantian apabila kata sandi lama tidak sesuai atau konfirmasi tidak cocok. |

### 3.2.21 Menampilkan Riwayat Donasi Pengguna
| | | |
|---|---|---|
| **ID Requirement** | : | FR SIKAS 210 |
| **Deskripsi** | : | Fungsi ini harus menampilkan seluruh donasi yang diajukan pengguna yang sedang masuk, beserta kegiatan tujuan, nominal, metode pembayaran, tanggal, dan status verifikasinya. Pengguna hanya boleh melihat donasi miliknya sendiri. |

### 3.2.22 Menampilkan Riwayat Keikutsertaan Relawan
| | | |
|---|---|---|
| **ID Requirement** | : | FR SIKAS 211 |
| **Deskripsi** | : | Fungsi ini harus menampilkan seluruh pendaftaran relawan yang diajukan pengguna yang sedang masuk, beserta kegiatan, jenis relawan, tanggal pendaftaran, dan status verifikasinya. Pengguna hanya boleh melihat pendaftaran miliknya sendiri. |

### 3.2.23 Menampilkan Notifikasi Pengguna
| | | |
|---|---|---|
| **ID Requirement** | : | FR SIKAS 212 |
| **Deskripsi** | : | Fungsi ini harus menampilkan riwayat pemberitahuan yang ditujukan kepada pengguna yang sedang masuk, beserta jenis pemberitahuan, judul, isi ringkas, dan waktu pembangkitannya. |

### 3.2.24 Memulihkan Kata Sandi
| | | |
|---|---|---|
| **ID Requirement** | : | FR SIKAS 213 |
| **Deskripsi** | : | Fungsi ini harus memampukan pengguna yang lupa kata sandinya menetapkan kata sandi baru melalui verifikasi surel. Sistem membangkitkan kode verifikasi enam digit, mengirimkannya ke alamat surel akun, serta menyimpannya paling lama **10 menit**. Kata sandi baru hanya diterima apabila kode yang dimasukkan sesuai dan belum kedaluwarsa, dengan panjang minimal delapan karakter beserta konfirmasinya. Kode bersifat **sekali pakai**, dan seluruh token akses yang masih aktif dicabut setelah kata sandi berhasil diganti. Setiap permintaan kode maupun penggantian kata sandi dicatat pada riwayat notifikasi. |

## C. Kelompok Partisipasi Masyarakat — penjabaran F-08 sampai F-10

### 3.2.24 Menyediakan Daftar Kegiatan Penerima Donasi
| | | |
|---|---|---|
| **ID Requirement** | : | FR SIKAS 301 |
| **Deskripsi** | : | Fungsi ini harus menyediakan pilihan kegiatan pada formulir donasi yang terbatas pada kegiatan berstatus aktif dan menyatakan membuka penerimaan donasi. Apabila tidak ada kegiatan yang memenuhi kriteria tersebut, sistem menampilkan keterangan bahwa donasi belum dapat diajukan. |

### 3.2.25 Mencatat Pengajuan Donasi
| | | |
|---|---|---|
| **ID Requirement** | : | FR SIKAS 302 |
| **Deskripsi** | : | Fungsi ini harus memampukan pengguna terdaftar mengajukan donasi dengan memasukkan kegiatan tujuan, tujuan donasi, nominal, metode pembayaran, dan pesan dukungan yang bersifat opsional. Nominal dapat dipilih dari nilai yang disediakan maupun diisi bebas tanpa batas maksimal. Data donatur diambil dari akun yang sedang masuk dan tidak dapat diubah pada formulir. |

### 3.2.26 Menolak Donasi tanpa Kegiatan yang Sah
| | | |
|---|---|---|
| **ID Requirement** | : | FR SIKAS 303 |
| **Deskripsi** | : | Fungsi ini harus menolak pengajuan donasi yang tidak menyertakan kegiatan, menyertakan kegiatan yang tidak membuka penerimaan donasi, atau menyertakan kegiatan yang tidak berstatus aktif. Penolakan harus dilakukan pada sisi layanan sehingga tetap berlaku meskipun permintaan dikirim tanpa melalui antarmuka. |

### 3.2.27 Menyediakan Pilihan Metode Pembayaran
| | | |
|---|---|---|
| **ID Requirement** | : | FR SIKAS 304 |
| **Deskripsi** | : | Fungsi ini harus menyediakan dua metode pembayaran, yaitu QRIS dan transfer bank, serta mencatat metode yang dipilih donatur pada data donasi. Metode yang dipilih menentukan bentuk instruksi pembayaran yang ditampilkan setelah donasi diajukan. |

### 3.2.28 Menampilkan Instruksi Pembayaran QRIS
| | | |
|---|---|---|
| **ID Requirement** | : | FR SIKAS 305 |
| **Deskripsi** | : | Fungsi ini harus menampilkan kode QRIS lembaga beserta nama *merchant* dan nomor identitas *merchant*, nominal yang harus dibayarkan, fasilitas penyalinan nominal, fasilitas pengunduhan gambar kode QRIS, serta langkah-langkah pembayaran. Sistem harus menyatakan secara jelas bahwa nominal tidak tertanam pada kode dan harus dimasukkan sendiri oleh donatur. Apabila berkas gambar kode QRIS tidak tersedia, sistem menampilkan keterangan yang dapat dipahami serta mengarahkan donatur ke metode transfer bank. |

### 3.2.29 Menampilkan Instruksi Transfer Bank
| | | |
|---|---|---|
| **ID Requirement** | : | FR SIKAS 306 |
| **Deskripsi** | : | Fungsi ini harus menampilkan nama bank, nomor rekening, dan nama pemilik rekening lembaga, beserta nominal yang harus ditransfer dan fasilitas penyalinan nomor rekening. |

### 3.2.30 Menerima Unggahan Bukti Pembayaran
| | | |
|---|---|---|
| **ID Requirement** | : | FR SIKAS 307 |
| **Deskripsi** | : | Fungsi ini harus menerima unggahan satu berkas gambar sebagai bukti pembayaran, menyimpannya pada penyimpanan berkas peladen, dan menautkannya pada data donasi yang bersangkutan. Sistem menolak berkas yang bukan gambar maupun yang berukuran melebihi 4 MB, disertai pesan kesalahan yang menjelaskan penyebabnya. Bukti dapat diunggah segera setelah donasi diajukan maupun kemudian melalui halaman riwayat donasi. |

### 3.2.31 Mencatat Donasi Anonim
| | | |
|---|---|---|
| **ID Requirement** | : | FR SIKAS 308 |
| **Deskripsi** | : | Fungsi ini harus memampukan donatur memilih agar identitasnya tidak ditampilkan. Donasi yang ditandai anonim harus ditampilkan tanpa nama donatur pada panel pengelolaan maupun berkas rekapitulasi, sedangkan keterkaitannya dengan akun tetap tersimpan pada basis data. |

### 3.2.32 Mencatat Pendaftaran Relawan
| | | |
|---|---|---|
| **ID Requirement** | : | FR SIKAS 309 |
| **Deskripsi** | : | Fungsi ini harus memampukan pengguna terdaftar mendaftar sebagai relawan pada kegiatan yang membuka kebutuhan relawan, dengan memasukkan jenis relawan, bidang minat, kemampuan diri, motivasi, kebutuhan khusus, dan nomor identitas kependudukan. |

### 3.2.33 Menyediakan Opsi Relawan sesuai Kegiatan
| | | |
|---|---|---|
| **ID Requirement** | : | FR SIKAS 310 |
| **Deskripsi** | : | Fungsi ini harus menampilkan pilihan jenis relawan dan bidang minat sesuai opsi yang ditetapkan pengelola pada kegiatan yang dipilih. Ketika pendaftar mengganti kegiatan, isi pilihan harus ikut menyesuaikan. Sistem harus memvalidasi pada sisi layanan bahwa pilihan yang dikirim termasuk dalam opsi kegiatan tersebut. |

### 3.2.34 Mengisi Data Pribadi Pendaftar secara Otomatis
| | | |
|---|---|---|
| **ID Requirement** | : | FR SIKAS 311 |
| **Deskripsi** | : | Fungsi ini harus mengambil nama, surel, nomor telepon, alamat, dan asal paroki pendaftar dari data profil akun, sehingga pendaftar tidak perlu mengisi ulang data yang telah tersimpan. |

### 3.2.35 Mengendalikan Kuota Relawan
| | | |
|---|---|---|
| **ID Requirement** | : | FR SIKAS 312 |
| **Deskripsi** | : | Fungsi ini harus membandingkan jumlah relawan yang telah diterima dengan kuota kegiatan, serta menampilkan keterangan dan menutup pendaftaran apabila kuota telah terpenuhi. |

| | | |
|---|---|---|
| **ID Requirement** | : | FR SIKAS 501 |
| **Deskripsi** | : | Fungsi ini harus menampilkan seluruh pendaftar relawan beserta nama, kontak, jenis relawan, kegiatan, dan status verifikasinya, dilengkapi pencarian berdasarkan nama atau surel serta penyaringan berdasarkan jenis relawan, status verifikasi, kegiatan yang diikuti, dan rentang tanggal pendaftaran. ### 3.2.49 Menetapkan Status Pendaftaran Relawan
| | | |

## Catatan penyusunan

**Penomoran ID sengaja tidak berurutan rapat dengan nomor subbab.** Nomor subbab (3.2.1 dan seterusnya) berjalan urut, sedangkan ID kebutuhan dikelompokkan per ratusan. Pemisahan ini memudahkan penyisipan kebutuhan baru di kemudian hari tanpa menomori ulang seluruh dokumen — misalnya kebutuhan pemulihan kata sandi kelak dapat masuk sebagai FR SIKAS 213 tanpa mengganggu nomor lainnya.

**Beberapa kebutuhan sengaja menegaskan "pada sisi layanan"**, yaitu FR SIKAS 206, 303, 310, 512, dan 513. Penegasan ini penting karena pembatasan yang hanya diterapkan di antarmuka dapat ditembus, dan hal tersebut merupakan pemenuhan langsung atas kekangan K-15 pada Subbab 2.4. Kelima butir itu pula yang menjadi dasar kasus uji keamanan pada dokumen pengujian.

**FR SIKAS 505 memuat ketentuan penanganan kegagalan** — kegagalan pengiriman surel tidak boleh membatalkan perubahan status. Ini bukan detail teknis semata, melainkan keputusan perancangan yang mencegah data pendaftaran menjadi tidak konsisten ketika peladen surel bermasalah, sejalan dengan kebergantungan D-02.

**FR SIKAS 213 ditambahkan belakangan.** Pemulihan kata sandi semula tidak dicantumkan karena implementasinya masih berupa simulasi pada sisi antarmuka sedangkan layanannya hanya kerangka kosong. Setelah fungsi tersebut dibangun sepenuhnya dan diuji, kebutuhannya dicantumkan. Penomorannya menyambung sebagai 213 tanpa mengganggu kode lain, sesuai alasan pengelompokan per ratusan di atas.

**Pengiriman pesan pada halaman Kontak tidak dicantumkan** sebagai fungsi karena formulirnya **dihapus** dari perangkat lunak pada 23 Agustus 2026; pertanyaan pengunjung diarahkan ke kanal WhatsApp resmi lembaga. Keputusan ini konsisten dengan Subbab 2.2 dan 3.1.1.
